# ZCNOVA BGM Studio 検査一式

`ZCNOVA_BGM_v5.6.html` を実際のブラウザで動かして確かめる、軽い検査です。
**「曲調Aを直したら曲調Bが壊れた」を機械的に見つける**のが一番の目的です。

## 用意するもの

Node.js 18 以上と Playwright（Chromium）だけです。

```bash
npm init -y                 # package.json が無ければ
npm i -D playwright
npx playwright install chromium
```

Playwright を全体に入れてある環境では、代わりに次を指定できます。

```bash
export ZC_PLAYWRIGHT=/usr/lib/node_modules/playwright/index.js
export ZC_CHROME=/path/to/chrome        # 使う Chromium を指定したいとき
```

## 走らせる

```bash
node tests/run.mjs          # 全部（およそ20〜60秒）
node tests/run.mjs 02       # 番号の合うものだけ
```

1つでも落ちれば終了コードは 1 です。

## 何を見ているか

| | 検査 | 中身 |
|---|---|---|
| ① | 生成の健全性 | 全31曲調 × 全5拍子 × 3種の小節数（465曲）を作り、**空のフレーズ・無音の小節・壊れた音名・例外**が出ないことを確かめる |
| ② | 指紋 | 決まった曲番号の62曲について、**パートごとに**指紋を取って控えと突き合わせる |
| ③ | SRI ハッシュ | HTML の `integrity` が `tests/vendor` の配信物と一致するか。ずれると**アプリが起動しない** |
| ⑥ | 昔の版の保存ファイル | 古い版で作った実物の `.json` が、いまの版でもそのまま開けるか |
| ⑤ | 曲のゆらぎ | 借りる候補が必ず同じカテゴリ内から来るか、同じ設定なら同じ曲になるか |
| ④ | 画面の通し操作 | 作る → 曲名 → 書き出し → トラック開閉 → 効果音レーン → 再生連打 を実際に押して、JSエラーが出ないこと |
| ㉑ | 音源スペックの指紋 | 32楽器のパラメーター（音域・倍音・ユニゾン・歪み・包絡線・ビブラート）を控えと突き合わせる |

※ 表は主なものだけです。⑦〜⑳（スラー・音域と音量・編成・軽さ・書き出し・独奏・公開用）は各 `cases/*.mjs` の先頭に、何のためにあるかが書いてあります。

## 曲の残し方 ― 大事な前提

**生成のしくみを直すと、同じたね（内部の乱数の種）からでも以前と同じ曲は
出ません。** たねは「作り方への入り口」なので、作り方が変われば出てくる曲も
変わります。この作業中も3回そうなりました（伴奏の変化 / ベースの乱数の
取り方 / 進行の選び方のバグ修正）。

そのため **画面から「曲番号」を控えて再現するしくみは撤去しました**
（SE番号も同じ理由で撤去）。守れない約束を画面に出しておくほうが害が
大きいためです。`song.seed` は生成の乱数源として内部には残っています。

曲を残す手段は2つに一本化しています。

- **💾 この曲を保存** … この端末（localStorage）に残す。手軽だが、
  ブラウザのデータを消すと消える。
- **⬇ ファイルに保存（.json）** … 音符そのものが入ったファイル。
  **版が変わっても必ず同じ曲が戻る**。長く残すならこちら。

検査 ⑥ が「最初の版」と「進行バグ修正の前」の実物のファイルで毎回
確かめています。書き出し済みの WAV / MP3 はもちろん影響を受けません。

## ② 指紋の使い方（ここが肝心）

指紋は「旋律1／旋律2／サブ／管／進行／ベース／ドラム／効果音／設定」の
**9項目に分けて**取っています。まとめて1つにすると、
「伴奏だけ直したつもりが旋律まで変わっていた」という取りこぼしが見えません
（実際にそれで乱数のズレを1度見落としています）。

落ちたときの読み方：

```
❌ 62曲 × 9項目 が控えと一致
    7箇所が変化（旋律1×1 / 進行×1 / ベース×1 …）
    - bright/2 の 旋律1
```

- **狙って変えた** → 控えを更新する
  ```bash
  ZC_UPDATE=1 node tests/run.mjs
  ```
  更新したときは、**どのパートがなぜ変わるのか**を必ずコミット文に書いてください。
- **触っていないはずのパートが変わっている** → まずそこを疑う。
  たいていは乱数の消費数が変わっています（`chance()` を条件付きで呼ぶと、
  呼ばれた回数が変わり、そのあとに作られるパートが全部ずれます。
  位置ごとの判定には `rnd()` を使わない `seedNoise()` を使ってください）。

## ㉑ 音源スペックの指紋（②とは別のもの）

②が見ているのは**音符**、㉑が見ているのは**音そのもののパラメーター**です。
片方だけでは足りません。楽器の値を取り違えても音符は1つも変わらないので、
②は通ってしまいます。

落ちたときは、どの楽器のどの値がどこからどこへ動いたかがそのまま出ます。

```
❌ 32楽器のパラメーターが控えと一致
    1楽器が変化
    - flute(木管): detuneMix 0.13→0.26
```

狙って変えたなら控えを取り直します。

```bash
ZC_UPDATE=1 node tests/run.mjs 21
```

控えのほかに、**控えを取り直しても効く検査**を置いてあります
（間違った値ごと控え直してしまう事故を止めるため）。

- 中身がまったく同じ楽器が2つ無いこと
- 管楽器のユニゾンが 0.25 以下（1人が1本を吹く楽器なので厚く積めない。
  アコーディオン＝1音に複数のリード、brass＝合奏 の2つだけ外してある）
- 掛けている楽器のビブラートが 3〜8Hz・60cent 以内
- 音域が 1〜5オクターブ、歪み・フィルタ・出力が取りうる値の中

## 仕組み

- `lib/serve.mjs` … Node 標準の http だけの配信サーバ。本体 HTML を読み込むとき、
  Tone.js と lamejs の読み込み先を `tests/vendor` の控えへ差し替えます
  （中身が同じでも URL が変わると `integrity` が効かなくなるので、そこは外します。
  ハッシュそのものの正しさは ③ で別に確かめています）。
  外部フォントの `<link>` も外します（ネットの有無で結果が揺れるため）。
- `lib/page.mjs` … ブラウザを開き、`pageerror` と `console.error` を集めます。
  ネットの遮断や Tone.js の作法警告は雑音として除きます。
- `cases/*.mjs` … 1本ずつが `name` と `run({ page, errors, root })` を持ち、
  `{ checks: [{ ok, label, info }] }` を返すだけです。増やすときは同じ形で置けば
  `run.mjs` が勝手に拾います。

## これで捕まえられないもの

- **音が良いかどうか**は見ていません（機械には判断できません）。
- 書き出した WAV / MP3 の中身は見ていません。
- iOS Safari など、実機でしか出ない不具合は見ていません。
